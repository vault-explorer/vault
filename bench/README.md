# Benchmarks

Measures Vault against the budgets in [docs/PERFORMANCE.md](../docs/PERFORMANCE.md), which also lists what is and isn't measured yet.

| Suite | What it measures | Runs on | Entry point |
| --- | --- | --- | --- |
| `core` | Directory listing, fuzzy matching | Windows, Linux, macOS | [`benches/core.rs`](benches/core.rs) (criterion) |
| `app` | Cold start, idle memory, scroll frame times | Windows | [`scripts/app-bench.mjs`](scripts/app-bench.mjs) |

Node 22 or later and the [normal build prerequisites](../README.md#building-from-source) are all you need. The scripts have no npm dependencies.

## Fixtures

The generator builds deterministic trees: the same seed gives the same paths, sizes, timestamps and contents on every OS. Names, extensions and sizes follow a realistic mix, including spaces, non-ASCII names and files with no extension. They go in `bench/fixtures/` (gitignored) unless you set `VAULT_BENCH_FIXTURES` or pass `--root`.

```sh
cargo run -p vault-bench --release --bin vault-fixtures -- generate               # flat-10k and flat-100k
cargo run -p vault-bench --release --bin vault-fixtures -- generate --include-1m  # adds nested-1m
```

The other commands are `verify` (checks a tree on disk against its manifest), `list` (shows planned sizes without touching the disk) and `clean`. Generating again skips trees that are already up to date.

| Tree | Files | Directories | Disk space | Generate on ext4 (WSL2) | Generate on NTFS, Defender on |
| --- | --- | --- | --- | --- | --- |
| `flat-10k` | 10,000 | 0 | ~200 MB | < 1 s | ~7 s |
| `flat-100k` | 100,000 | 0 | ~1.9 GB | ~6 s | ~75 s |
| `nested-1m` (opt-in) | 1,000,000 | 50,000, up to 10 levels deep | ~19 GB | ~100 s | Not run yet; expect about 15 minutes |

Disk space was measured on ext4 with `du`. It will differ a little on NTFS.

`nested-1m` is never generated by default or in CI. No bench uses it yet; it's ready for the MFT prototype.

File contents are pseudo-random and sizes stop at 4 MiB, so real media files would be larger. Listing only reads metadata, so bigger files would cost disk space and measure nothing.

## Running the benches

Run from the repo root. Results go to `bench/results/` (gitignored) unless you pass `--out`.

### On Windows

```powershell
pnpm bench                        # both suites; builds the app first
pnpm bench --suite core           # listing and fuzzy matching only
pnpm bench --suite app --no-build # reuse the binaries from the last run
```

A full run takes about 8 minutes on a 6-core desktop with the Rust dependencies already built, or 4 minutes with `--no-build`. Options: `--runs <n>` (default 5), `--settle <seconds>` (default 30), `--repo <dir>`, `--out <dir>`.

The app suite opens real windows, and they must stay visible, because a covered or hidden WebView2 stops rendering. Leave the machine alone while it runs, and close heavy apps first. Numbers depend on the monitor too: a 240 Hz display reports frame intervals near 4 ms, while 60 Hz reports near 16.7 ms.

### In WSL

WSL runs only the `core` suite:

```sh
pnpm bench   # defaults to --suite core outside Windows
```

Keep the repo and fixtures on the Linux file system. These numbers measure ext4 on Linux, and Vault's budgets are defined on Windows, so use them to compare changes rather than to check budgets. `/mnt/c` goes through a translation layer and measures that layer instead.

For the `app` suite, use a separate Windows checkout on an NTFS drive and call Windows tools from WSL. Don't run Windows tools against a `\\wsl$` path.

```sh
cd /mnt/d/vault && cmd.exe /c "pnpm install && pnpm bench"
```

## Reading results

Each suite writes one JSON file. `compare.mjs` takes two files, or two directories of them, and prints a Markdown table. It always exits 0 on valid input.

```sh
pnpm bench:compare path/to/base path/to/head
```

| Column | Meaning |
| --- | --- |
| Base, Head | Median of all samples |
| Change | Head against base. ⚠ marks an increase above 10%, so a slowdown or more memory |
| Budget | The limit. `*` means the metric covers only part of what the budget promises; a note under the table says which part |
| Result | Head against the budget: `pass` or `FAIL`. `–` means the metric has no budget |

A `pass` with a `*` doesn't mean the budget is met. A difference of a few percent on a shared CI runner may be noise; see [ADR 0014](../docs/adr/0014-report-only-bench-ci.md).

### Result format

```jsonc
{
  "schema_version": 1,
  "suite": "core",
  "commit": "5b35fa7…",
  "machine": { "os": "windows", "arch": "x86_64", "logical_cores": 12, "cpu": "…", "ram_gb": 16, "os_build": "10.0.19045", "disk": "…" },
  "metrics": [
    {
      "name": "dir_list.10k.full",   // A key in budgets.json
      "value": 12.3,                 // Median
      "unit": "ms",
      "p95": 14.1,
      "samples": 20,
      "budget": 300,                 // null if this metric has no budget
      "budget_op": "<",              // "<" or "<=", null if no budget
      "scope": "core listing only…", // null if the metric covers the whole budget
      "cache": "warm"                // File-system cache state
    }
  ]
}
```

Running `cargo bench` directly also writes this file, but only `run.mjs` adds `cpu`, `ram_gb`, `os_build` and `disk`.

## Adding a metric

1. Add it to [`budgets.json`](budgets.json) and to the metrics table in `docs/PERFORMANCE.md`. A test fails if they disagree.
2. Measure it in `benches/core.rs` or `scripts/app-bench.mjs`. Call the real crate API, never a stand-in.

## In CI

The `bench` job in [`.github/workflows/ci.yml`](../.github/workflows/ci.yml) runs on every PR. It builds and benches the PR's merge base and head in one `windows-latest` job, and posts the table to the job summary. It never fails the build. If the base predates the harness, the job measures head against itself, so every change in that table is runner noise.
